# Workspace routing model

Agent Tick uses Workspace as the top-level container for members, agents, routing rules, and activity history. Every human has an Agent Tick-owned Personal Workspace fixed-name “Personal” for individual setup, and shared work uses separate Shared Workspaces. A Shared Workspace may be backed by a Clerk Organization for membership/account management, but Agent Tick presents it as a Shared Workspace and mirrors Clerk organization roles to Agent Tick Owner/Admin/Member roles. Where Clerk Organizations are unavailable, Agent Tick manages the same Owner/Admin/Member roles itself. Approval devices belong to humans by default; workspace-specific routing or member preferences can narrow which devices receive activity. Agent Tokens are the server-side identity for agent actors. Shared Workspace Agent Tokens carry an Agent Assignment to a Routing Rule, which decides which Workspace Members receive Status Updates, Steering, and Sanctions. Client, host, folder, CI, and coding-agent names are metadata on activity from that token rather than separate managed Agent identities. Teams, projects, schedules, and policies are not separate product pillars or database types; they are user-named or configured Routing Rules. Personal and shared use cases are the same model with different available options: a one-member Workspace implicitly routes each agent to its sole member, while multi-member Workspaces require explicit Routing Rules before agent activity is usable and can expose member selection, scheduling, and quorum routing.

This replaces a split mental model of single-user mode versus multi-user shared mode. The server should not need separate product modes for routing semantics; it can expose capabilities according to the Workspace's membership, entitlement, and configured Routing Rules. Hosted, self-hosted, Clerk, and local access differences are authentication/deployment concerns rather than separate product capability models.
