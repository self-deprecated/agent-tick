# Private Requests server-opaque encryption

Agent Tick supports Private Requests as a server-opaque Request content mode: Request content is encrypted before it reaches Agent Tick servers, and the private keys needed to decrypt it remain on Approval Devices. The goal is to keep Request titles, bodies, commands, choice labels, question text, and sensitive presentation/session metadata unreadable to normal Agent Tick server storage, databases, backups, logs, and admin tools, while preserving Agent Tick's ability to route Requests, track pending/responded state, deliver push notifications, and return bounded responses to the originating agent.

This is a server-opaque storage and routing design, not a malicious-server-proof end-to-end encryption claim. The server still resolves recipients and supplies device public keys to the CLI or integration creating the Activity. A compromised or malicious server could substitute public keys unless a future key verification, pinning, transparency, or out-of-band trust model is added. The public security claim is that sensitive stored Activity content is encrypted for Approval Devices and unavailable to routine server storage, backups, logs, and admin tools; it is not complete protection from an actively malicious Agent Tick service.

Each Approval Device owns its own encryption keypair. The private key is generated and stored on that app installation and is never uploaded to Agent Tick. The public key is registered with the server as an active device key. Device keys are per device, not per user, Workspace, Routing Rule, or Agent Connection. A user with an iPhone and an iPad has two private keys and two public keys. A user who belongs to multiple Workspaces may use the same device public key in all of those Workspaces; Workspace access is determined by membership and routing, not by creating different encryption identities per Workspace.

The Native App should implement device-key operations using platform-provided cryptography and secure storage. On iOS, use Apple-provided APIs such as CryptoKit, Security.framework, and Keychain/SecureStore rather than bundled custom or third-party crypto libraries. On Android, use Android platform cryptography and Android Keystore equivalents. This keeps the mobile app's App Store and Play Store compliance story as simple as possible while still making server-stored Request content opaque. The CLI is not part of the iOS App Store binary and may use Node's standard cryptography APIs for encryption.

When a CLI or integration creates a Private Request, it first asks the server for a private Request encryption context using only non-sensitive routing information. The server resolves the same recipients it would use for a normal routed Request and returns the currently active encryption-capable Approval Device keys for those recipients, plus enough context to detect recipient/key changes before creation. The CLI then generates one random per-Request symmetric content key, encrypts the sensitive Request payload once with that content key, and wraps that content key separately for every returned device public key. The server stores the encrypted payload and one key envelope per target device key.

A Private Request's recipient device set is frozen at creation. Devices added after creation can decrypt future Private Requests but not old ones. Devices revoked before creation must not receive new envelopes. There is no launch requirement to sync private keys between devices, recover old private history on a new device, or rewrap existing Requests for newly added devices. Those recovery and rewrap flows may be added later if the product needs them, but they are not part of the current trust model.

Private Request enforcement is configurable at Workspace, Routing Rule, and CLI levels. A Workspace or organization may require private encryption globally or for a specific route. A CLI configured for required private mode must fail closed: it must use the private prepare/encrypt/create flow and must never silently downgrade the Request to plaintext. If the server reports that private encryption is required for the selected Workspace or Routing Rule, the CLI must follow that requirement even if local CLI defaults would otherwise allow plaintext.

Partial device-key failure should not block a Request for everyone. If some eligible recipients or devices are in a broken encryption state, the server should exclude those broken device keys from the encryption context, mark those devices or recipients as unable to receive/decrypt this Private Request, and allow the CLI to create the Request for the recipients/devices that are correctly configured. Only if no eligible recipient has any usable encryption-capable Approval Device should required private creation fail. In that all-missing case, the CLI should fail before creating a plaintext or unreadable Request and explain that no recipient has a usable Private Request device key.

The app should surface encryption setup and failure states clearly. If a user is eligible for a Private Request but the current device did not receive a usable envelope, cannot find its local private key, or fails to unwrap/decrypt the payload, the Native App should show a local failure state such as “This Private Request can't be opened on this device” and direct the user to set up or repair Private Request encryption. If another device for the same user received a valid envelope, that other device may still open and answer the Request. If a device is missing or broken, repairing encryption affects future Private Requests by registering a fresh usable public key; it does not imply that the device can decrypt historical Requests unless a later rewrap/recovery design is implemented.

The server should keep enough non-sensitive cleartext to operate the product. Clear fields may include Workspace, Routing Rule, Request type, status, deadline, response policy, recipient rows, waiter liveness, creation/responded timestamps, test flags, and opaque identifiers. Sensitive display content should live in the encrypted payload. For Private Requests, push notification payloads must remain minimal and must not include decrypted Request content.

Responses are intentionally simpler. Private Requests may return clear bounded response identifiers such as `approve`, `deny`, or selected option IDs, because Agent Tick still needs to finalize Requests, satisfy quorum, and return a machine-readable bounded result to the originating agent. Those bounded identifiers are visible operational data, not encrypted display content. Freeform response text should be disabled for Private Requests until encrypted response payloads are designed. Encrypting responses back to an agent-provided ephemeral public key is a future extension, not part of the current trust model.

The create flow should be race-safe. The server should return a recipient/key version or context identifier when preparing encryption. The CLI must include that context when it uploads the encrypted Request. If routing membership, availability, or active device keys change in a way that invalidates the prepared context before creation, the server should reject the create with a retryable recipients-changed error. The CLI should then prepare again, re-encrypt with the new device key set, and retry. Required private mode still fails closed if the retry cannot produce any usable recipient device envelopes.

This design gives Agent Tick practical Private Requests: private keys are per device, correctly configured devices can receive encrypted Request content even when other devices are broken, organizations can require private mode for Workspaces or routes, and the CLI always encrypts when private mode is required or configured. It deliberately avoids key synchronization, historical recovery, encrypted responses, and malicious-server-proof key verification in the current public trust model.

## Addendum: server-wide policy

In addition to the per-Workspace and per-Routing-Rule `privateRequestsRequired` toggles, a deployment operator can set a server-wide policy (`AGENT_TICK_PRIVATE_REQUESTS_POLICY`, also exposed as the NixOS option `services.agent-tick.privateRequestsPolicy`) with three values:

- `off` (default): each Workspace and Routing Rule decides via its own stored toggle.
- `default`: newly created Workspaces are seeded with Private Requests required, but Workspace Owners can still toggle them off.
- `forced`: Private Requests are required for every Workspace and Routing Rule on the server regardless of stored toggles, and attempts to disable the toggle are rejected with HTTP 409 `private_required_forced`. Plain CLI requests are rejected with HTTP 409 `private_required`.

The store's single `privateRequired()` source of truth ORs the forced policy together with the stored Workspace/Routing-Rule flags, so request creation, the `private-requests/prepare` `required` flag, and the Console's locked toggle state all agree. The current server policy is exposed to the Console via `GET /v1/me` as `privateRequestsPolicy` so the UI can render the toggle locked when the server forces encryption.
