# Private encryption

Agent Tick can store some Activity content as **private encrypted content**. Private encryption is used for Private Requests and private full-reply Status Updates when an integration or Workspace enables it.

The goal is server-opaque storage and routing: Agent Tick servers can route Activity, track status, send minimal notifications, and return bounded responses, while sensitive display content is encrypted for Approval Devices. This is different from malicious-server-proof end-to-end encryption; see [Server trust model](#server-trust-model).

## Where the key lives

Each Approval Device has its own private encryption key pair.

- The key pair is generated by the Agent Tick app on that device.
- The private key is stored on that device using platform-provided secure storage.
- The private key is not uploaded to Agent Tick servers.
- The app registers only the matching public key with each Agent Tick server/account connection.

On iOS, Agent Tick uses Apple platform cryptography and secure storage APIs. On Android, Agent Tick uses Android platform cryptography and Android Keystore-style storage.

## What the server stores

For private encrypted Activity, Agent Tick servers store:

- non-sensitive routing and timeline metadata such as Workspace, status, timestamps, and recipient/device identifiers;
- an encrypted payload containing the private display content;
- encrypted key envelopes for the recipient device public keys.

The server does not receive the device private key needed to decrypt the payload. It does still store and process the clear operational fields needed to deliver the product.

## How multiple recipients work

Private Activity uses an envelope model when an agent sends one Request or Status Update to multiple users or devices.

1. The creating integration asks the server for the currently eligible recipient device public keys.
2. The integration creates one random content key for this Activity item.
3. The sensitive payload is encrypted once with that content key.
4. The content key is then wrapped separately for every recipient device public key, producing one key envelope per target device key.
5. The server stores the single encrypted payload plus the set of device key envelopes.

Each recipient device uses its own local private key to unwrap only its envelope, then decrypts the shared encrypted payload. This means one private Request can be delivered to several users and to several devices per user without uploading any device private key to the server.

The recipient device set is frozen when the Activity is created. A device added later can receive future private Activity, but it cannot decrypt older payloads unless a future rewrap/recovery flow is added. A revoked or missing device key should not receive new envelopes.

## What can still be visible

CLI and MCP callers can request private Activity with `--private` or `contentMode: "private"`, or set `privacy.defaultContentMode` in `agent-tick features` config. For rich agent message mirroring, thinking, and detailed Tool Activity, enable **Private encryption** in the Native App at **Settings → General** first, then make private encrypted Activity the saved default. Private mode encrypts sensitive display payloads, but it still sends generic public labels so timelines and notifications remain usable.

Private encryption is not a replacement for normal operational security. Agent Tick may still store or process non-sensitive operational fields in cleartext, such as:

- Workspace and Routing Rule identifiers;
- Request type, status, deadlines, and response policy;
- Session identity and timestamps;
- generic notification-safe labels such as “Assistant replied”;
- bounded response identifiers such as `approve`, `deny`, or selected option IDs.

Do not put secrets in clear operational fields, titles, logs, diagnostics, analytics, or notification copy.

## Server trust model

Private encryption is designed to make stored Request and Status Update content opaque to normal Agent Tick server storage, backups, logs, and admin tools.

It is not currently a malicious-server-proof end-to-end encryption system. The server supplies recipient public keys during private content creation. A compromised or malicious server could substitute keys unless a future key transparency, pinning, or out-of-band verification model is added.

Agent Tick's current public claim is therefore server-opaque storage and routing: sensitive display payloads are encrypted for Approval Devices and should not be readable through normal server databases, backups, logs, or admin tools. It is not a claim that an actively malicious server cannot interfere with key selection, metadata, routing, or bounded response processing.

## Multiple devices and old Activity

Device keys are per app installation. If you use Agent Tick on more than one phone or tablet, each device has its own private key and its own public key registration.

Repairing key registration affects future private Activity. Older private Activity may remain locked on a device if it was created before that device key was registered, after a previous key was replaced, or for another Approval Device.

## Checking setup in the app

In the Native App, open **Settings → General → Private encryption**.

That view shows whether:

- native private encryption is available in this build;
- this device has a local private encryption key;
- each saved server/account connection has a matching active public key registration;
- a connection needs repair.

Use **Repair registration** to re-register this device's public key with saved Agent Tick server connections. This does not show or upload the private key.
