Agent Tick Mobile Multi-login Token Flow

A single-page map of what should happen when a mobile user signs into one Clerk account, adds another, then switches between them.

Core idea: Clerk is only used to prove identity during sign-in. The durable app session is an Agent Tick mobile session JWT, saved once globally as the active account and once per saved account.

Token and storage legend

Clerk token/client token

Short-lived sign-in proof from Clerk/native Clerk. Used to call POST /v1/auth/mobile-session.

Agent Tick mobile session JWT

Durable app token minted by Agent Tick. Used for mobile API calls in Clerk mode.

Active account key

__agent_tick_mobile_session_jwt
Contains the currently selected account JWT.

Per-account key

agent-tick.mobileAccountSession.<account id>
Contains each saved account JWT.

Saved account list

agent-tick.mobileAccounts
Account switcher entries.

Device/push state

agent-tick.session.<server>.deviceID, organizationID, pushStatus.

Main flow

Split into three smaller diagrams so the whole state transition is visible without panning around one huge graph.

1. Initial login

flowchart TD
  Start([App starts]) --> Config[Fetch /v1/auth/config]
  Config --> ClerkMode{Clerk mode?}
  ClerkMode -- no --> Local[Local / single-mode pairing]
  ClerkMode -- yes --> SignInA[Show Clerk sign-in]
  SignInA --> ClerkA[User signs into Clerk account A]
  ClerkA --> LoginA[Get Clerk token/client token]
  LoginA --> MintA[POST /v1/auth/mobile-session]
  MintA --> JwtA[Agent Tick JWT A]
  JwtA --> StoreA[Save JWT A:
active key
per-account A key]
  StoreA --> SignOutA[Sign out native Clerk]
  SignOutA --> AppA[Use JWT A for API calls]
  AppA --> ProfileA[Load me, orgs, approvals]
  ProfileA --> SaveA[Saved accounts = A]
  SaveA --> PushA{Push registered
while A active?}
  PushA -- yes --> DeviceA[Device row:
user A + org A + Expo token]
  PushA -- no --> NoPushA[A may not get remote pushes]

2. Add another account

flowchart TD
  AppA[Currently active: JWT A] --> AddB[Tap Add another account]
  AddB --> PrepB[addingClerkAccount=true
clear clerkLoginToken
JWT A remains until replaced]
  PrepB --> ClerkOut[Sign out Clerk/native Clerk]
  ClerkOut --> SignInB[Show Clerk sign-in]
  SignInB --> ClerkB[User signs into Clerk account B]
  ClerkB --> LoginB[Get Clerk token/client token B]
  LoginB --> MintB[POST /v1/auth/mobile-session]
  MintB --> JwtB[Agent Tick JWT B]
  JwtB --> StoreB[Active key = JWT B
per-account B key = JWT B
per-account A key still JWT A]
  StoreB --> SignOutB[Sign out native Clerk again]
  SignOutB --> AppB[Use JWT B for API calls]
  AppB --> ProfileB[Load B me, orgs, approvals]
  ProfileB --> SaveB[Saved accounts = B, A]
  SaveB --> PushB{Push registered
while B active?}
  PushB -- yes --> DeviceB[Device row:
user B + org B + Expo token]
  PushB -- no --> NoPushB[B may not get remote pushes]

3. Switch between saved accounts

flowchart TD
  SwitchA[Select account A] --> ReadA[Read per-account JWT A]
  ReadA --> ValidateA[Validate with /v1/me]
  ValidateA --> ActiveA[Active key = JWT A]
  ActiveA --> ClearA[Clear visible requests/history/org]
  ClearA --> ReloadA[Reload A profile, orgs, approvals]

  ReloadA --> SwitchB[Select account B]
  SwitchB --> ReadB[Read per-account JWT B]
  ReadB --> ValidateB[Validate with /v1/me]
  ValidateB --> ActiveB[Active key = JWT B]
  ActiveB --> ClearB[Clear visible requests/history/org]
  ClearB --> ReloadB[Reload B profile, orgs, approvals]

Desired notification model

Account A notifications

flowchart TD
  Phone[One phone / app install
same Expo push token] --> AccountA[Saved account A
JWT A]
  AccountA --> DeviceA[Server device row A
user A + org A + Expo token]
  ApprovalA[Approval in org A] --> LookupA[Server lists org A push devices]
  LookupA --> DeviceA
  DeviceA --> PushA[Expo push to phone]
  PushA --> OpenA[Switch to A to view/respond]

Account B notifications

flowchart TD
  Phone[One phone / app install
same Expo push token] --> AccountB[Saved account B
JWT B]
  AccountB --> DeviceB[Server device row B
user B + org B + Expo token]
  ApprovalB[Approval in org B] --> LookupB[Server lists org B push devices]
  LookupB --> DeviceB
  DeviceB --> PushB[Expo push to phone]
  PushB --> OpenB[Switch to B to view/respond]
Important: receiving notifications for all saved accounts requires each account/org to have its own server-side device row with the Expo push token. The user may still need to switch accounts in the app to see the matching approval list.

Likely bug zones

  • Push registration may only happen for the active account. Adding account B does not necessarily register the Expo push token for B.
  • Device/push state is server-scoped, not account-scoped. Multiple Clerk accounts on the same server can share local deviceID, organizationID, and pushStatus keys.
  • Account switching changes the active JWT, but may leave stale push/device state. The UI may think push is registered for the newly selected account when the server row belongs to another account/org.
  • Notification payloads do not appear to carry enough account/org routing context. A tap can select a request id, but the app may not know which saved account should be activated automatically.

Compact state table

After account A login

  • Active key = JWT A
  • Per-account A key = JWT A
  • Saved accounts = A
  • Push works for A only if registered while A active

After adding account B

  • Active key = JWT B
  • Per-account A key = JWT A
  • Per-account B key = JWT B
  • Saved accounts = B, A
  • Push for B requires B device registration

After switching to A

  • Read per-account A key
  • Validate JWT A with /v1/me
  • Active key = JWT A
  • Reload A orgs and approvals

After switching to B

  • Read per-account B key
  • Validate JWT B with /v1/me
  • Active key = JWT B
  • Reload B orgs and approvals
